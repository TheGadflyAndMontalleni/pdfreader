# 分析报告：SumatraPDF 是怎么做的，以及我为什么不照着做

这份文档记录两件事：

1. 对 SumatraPDF 3.6.1 安装包的**取证分析**和**源码分析**结论；
2. 由此得出的**本项目设计决策** —— 哪些对齐了，哪些刻意没有对齐，为什么。

> **方法说明。** 本文属于**封装层取证 + 源码分析**，不是完整的二进制逆向。
> 安装包是自解压程序，我解析了它的封装格式、用 Ghidra 做了自动分析并读了关键
> 字符串与函数，同时下载了对应的上游源码做交叉印证。
> **我没有做的事情也要说清楚**：Ghidra 在安装包里识别出 5,642 个函数，我实际
> 反编译的是其中极少数；`src/` 目录的阅读量约 0.35%。下文凡是推断而非直接观测的
> 结论都会标注出来。

---

## 1. 安装包的封装格式

| 项 | 观测结果 |
|---|---|
| 文件类型 | PE32+ (x64) 可执行，非 MSI、非 Inno、非 NSIS |
| 数字签名 | **有效**，`CN=Krzysztof Kowalczyk`，签发者 Certum |
| 载荷位置 | `.rsrc` 节，RCDATA 资源 |
| 容器魔数 | `0x41537a4c`（ASCII `LzSA`） |
| 实际压缩 | **不是 LzSA，是 LZMA + x86 BCJ 过滤器** |

最后一条是这个安装包最有意思的地方：**容器自称 LzSA，里面的数据却是 LZMA**。
这是通过逐条比对上游 `MakeLZSA.cpp` 的写法确认的，不是猜的。

### 容器格式

来自 `MakeLZSA.cpp` 的结构定义，并用真实字节逐字段验证过：

```
偏移 0    u32  magic = 0x41537a4c ("LzSA")
偏移 4    u32  fileCount
之后每项：
          u32  headerSize      = 25 + nameLen
          u32  compressedSize
          u32  uncompressedSize
          u32  crc32
          u32  mtimeLo
          u32  mtimeHi
          u8[] name (nameLen 字节) + NUL
全部项之后：
          u32  headerCrc32
然后：    各文件压缩数据依次拼接
```

单个数据块的首字节决定解压方式：

```
0xFF                     → 原样存储（kStoredMarker）
否则 第 1 字节 = BCJ 标志
     第 2..6 字节 = LZMA 属性（5 字节）
     之后         = 裸 LZMA1 流
```

### 我在这里踩的坑

第一版解出来的 `libmupdf.dll` 是**机器码而不是 PE 文件**。原因是我把
`dataOff` 当成了文件绝对偏移，实际上它是**相对于数据区起点**的。
发现方式是一个容量自洽检查：`0x7E + 6,987,217 = 6,987,343`，
正好等于 RCDATA/1 资源的大小 —— 说明基址算错了，不是数据坏了。

修正后解出：

| 文件 | 大小 |
|---|---|
| `libmupdf.dll` | 16,625,528 B |
| `PdfPreview.dll` | 746,360 B |
| `PdfFilter.dll` | 342,904 B |
| 文档 | 49 个 |

**`SumatraPDF.exe` 不在载荷里。** 安装包自身的 `.text` 节就是阅读器主体 ——
这一点一开始让我找错了分析对象。

| 地址 / 字符串 | 含义 |

| `0x140170370` 附近，断言 `!win->tocLoaded` | 目录面板的装载状态断言 |

## 3. 决定性的发现：SumatraPDF 没有自动目录

下载上游源码后，`src/TableOfContents.cpp` 给出了明确答案。这个文件**只负责显示**，
而且装载路径上有一个提前返回：大纲为空就直接不做了。

```cpp
auto* tocTree = tab->ctrl ? tab->ctrl->GetToc() : nullptr;
if (!tocTree || !tocTree->root || !tocTree->root->child) {
    return;   // 没有内嵌大纲 → 什么都不显示
}
```

（上为语义等价摘录，非逐字引用。）

**结论：SumatraPDF 的目录完全来自 PDF 内嵌的 `/Outlines`。
文档没有大纲，侧边栏就是空的。它不做印刷目录页识别，也不做版式推断。**

### 这对本项目意味着什么

用户的核心需求 —— "不管原来的 PDF 带不带大纲都能在侧边栏生成可跳转的目录" ——
**不是移植，是净新增能力**。SumatraPDF 在这里没有可抄的东西。

所以本项目的目录引擎是独立设计的（四层策略，见 [README](../README.md#5-自动目录--核心差异能力)）：

- **L0 内嵌大纲**：对齐 SumatraPDF 的行为；
- **L2 印刷目录页**：SumatraPDF 没有；
- **L3 排版推断**：SumatraPDF 没有。

### L3 的设计依据来自实测，不是灵感

L3 的第一版误检极其严重：一份 17 页的文档产出 **313 条**"标题"，
两份直接顶到 500 条上限。抽样一看，正文段落被当成了标题。

四次测量驱动的修正（每一次都是先量化、再定位根因）：

| 版本 | 节点数 | 暴露的问题 |
|---|---|---|
| v1 | 313 / 500+ / 500+ | 把 `bold` 当成绝对信号 |
| v2 | 297 / 500 | 修了 bold 仍泛滥 |
| v3 | **15** / 62 | 改用**每页中位高度**作局部基准 |
| v4 | 9 / 40 | 精度上去了，但**丢了同字号章节标题** |
| v5 | **17** / 40 | 编号序列恢复，八个章节全部找回 |

两个根因值得记下来：

1. **绝对信号不可用。** 整篇文档正文都是粗体时，`bold` 的区分力是零。
   所有版式信号都必须**相对于本文档、本页面的基准**。

2. **全局统计量会被异常区域带偏。** 按字符数取众数求"正文高度"，
   在表格密集的文档里众数是表格文字（7.5pt），正文段落（15pt）于是成了"2 倍于正文"。
   **改用每页中位数**才修好。

而"与正文完全同字号"的章节标题（`一、概述` 这类）任何版式信号都抓不到，
最后是靠**换维度**解决的：递增的顶层编号序列本身就是一份目录。

## 4. 为什么标注不是真注释

实现标注功能时，我先查 PDFium 的注释 API 面：

- `FPDFPage_CreateAnnot(page, subtype)` ✔
- `FPDFAnnot_SetRect` / `SetColor` / `SetStringValue` ✔
- **`/QuadPoints` 的 setter ✘ —— 不存在**

文本标记注释（高亮/下划线/删除线/波浪线）**渲染时读的是 `/QuadPoints`**。
只设 `/Rect` 造出来的注释，会在文件里存在、在**任何阅读器里都不可见**。

那会是一个"测试通过、用户看不见"的假功能。所以我改成把标记**烘焙进页面内容**
（`FPDFPageObj_CreateNewRect` + `FPDFPage_InsertObject` + `FPDFPage_GenerateContent`），
代价是单向、不可交互编辑。

验证方式也相应改成**像素级**：视口图像差分证明它可见（2964 像素变化），
撤销后回到 0，保存后重新打开文件仍有 1093 像素 —— 而不是去断言"注释对象存在"。

## 5. 与 SumatraPDF 的对齐情况

### 已对齐

| 能力 | 说明 |
|---|---|
| 连续滚动阅读 | 整篇一条页面长条 |
| 缩放 | 适应宽度 / 适应页面 / 单页视图 / 连续视图 |
| 键盘导航 | PageUp/Down、Space、Home/End、方向键 |
| 文字选择与复制 | 跨行跨页，中日韩不插空格 |
| 查找 | F3 循环、大小写选项、命中高亮 |
| 标签页 | 每标签独立的阅读位置与视图状态 |
| 最近文件 / 记住位置 | 跨进程持久化 |
| 打印 | 支持页码范围 |
| 反色 | 夜间阅读 |
| 缩略图侧栏 | 懒生成 |
| 标注 | 高亮 / 下划线 / 删除线 |
| 目录面板 | 含跳转 |

### 刻意没对齐

| 能力 | 原因 |
|---|---|
| 直接复用其源码 | GPL-3.0 会传染，与"属于自己的软件"目标冲突 |
| EPUB / CBZ / DjVu / CHM / XPS | 需要额外的格式层，超出本轮范围 |
| 命令面板、可自定义快捷键 | 优先级低于核心阅读体验 |
| 矢量打印到物理打印机 | PDFium 公开 API 不提供 |

## 6. 复现这份分析

```powershell
# 1) 安装包取证（PE 资源、签名、容器结构）
pwsh -NoProfile -File tools/build.ps1      # 与本分析无关，仅说明工具链
python tools/extract_lzsa.py <installer.exe> <outdir>
python tools/probe_lzsa.py <installer.exe>

# 2) 二进制分析（需要 REA + Ghidra）
#    REA_ANALYSIS_PROVIDER=ghidra, GHIDRA_INSTALL_DIR, JAVA_HOME
rea analyze <installer.exe> --snapshot ghidra-sumatra.snap

# 3) 上游源码交叉印证
#    src/TableOfContents.cpp、MakeLZSA.cpp 来自 sumatrapdf 上游仓库
```

数据与结论的对应关系：第 1 节来自容器解析脚本的逐字段校验；
第 2 节来自 Ghidra 快照与 REA 查询；第 3 节来自上游源码；
第 4 节来自 PDFium 头文件 `fpdf_annot.h` 的 API 面清点。
